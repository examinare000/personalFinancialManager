# ADR-006: 取引の冪等性確保にhash UNIQUE制約を採用

## ステータス
採用済み

## 背景

本アプリケーションは公式 CSV を週次で手動 DL して取り込む方式（→ ADR-001）を採用しており、以下のシナリオが日常的に発生する。

- 前週の取り込み済み CSV を誤って再投入してしまう
- 銀行ダイレクトの保存期間制約（設計書 §5.1 で MUFG は短い）から、毎月初に過去分を含めて DL する
- パーサ改修後、原本（`raw_payload`）を保持しているため再パース・再 INSERT する運用シナリオ

これらの場面で、同一取引が二重に INSERT されるとデータ整合性が破綻する。設計書 §9.3 では「同じ CSV を 2 回取り込んでも重複しない」が冪等性の検証ポイントとして明記されている。

## 検討した選択肢

### 選択肢A. 自然キー（機関側の取引 ID）を UNIQUE にする
- メリット: 機関が ID を提供しているなら最も素直
- デメリット: 銀行 CSV の多くは取引 ID を提供していない。EC メール由来は ID 体系がそもそも存在しない。機関横断で統一できない

### 選択肢B. 複合 UNIQUE 制約 `(account_id, occurred_on, amount, description)`
- メリット: 列単位で意味が明確、SQL から見て理解しやすい
- デメリット: `description` が長文・改行を含むケースがあり、UNIQUE 索引のキー長やパフォーマンスに影響する。同日同額同摘要の正当な重複（同店で 2 件購入等）の判定が難しい

### 選択肢C. ハッシュ UNIQUE 制約（`(account_id, occurred_on, amount, description)` の SHA-256）
- メリット: 索引キーは固定長、複合キーの意味は維持しつつインデックス効率が高い、追加列を含めたい場合の拡張性
- デメリット: ハッシュ衝突理論上はゼロでない（SHA-256 で実用上ゼロ）。SQL から目視で意味が読めない

## 決定

選択肢 C を採用する。設計書 §4.2 / §4.3 のとおり、`transactions.hash` 列に
`SHA-256(account_id || occurred_on || amount || description)` を格納し、UNIQUE 制約を付与する。

## 理由

- 機関 ID に依存しないため、すべての取込経路（CSV / メール / 公式 API）で統一的に冪等性を保証できる
- 索引キーが固定長になるため、複合 UNIQUE 制約より索引サイズが安定する
- SHA-256 衝突は実用上ゼロであり、家計データ規模では現実問題にならない
- 「同店同額同日 2 回」の正当な重複は、`occurred_at`（時刻）や `description` の差分でハッシュ値が変わるため、ハッシュ生成キーの設計次第で吸収できる。逆に時刻が無い CSV では重複扱いとなるが、これは運用上許容（手動分割が必要なケースのみ手動入力で対応）

## 結果

- 取込時は `INSERT ... ON CONFLICT (hash) DO NOTHING` で冪等性を確保
- ハッシュ生成ロジックは共通モジュール化し、アダプタが直接 `hash` を計算しない（テスト容易性）
- ハッシュキーに含める列を将来変更する場合は、過去レコードの再ハッシュが必要となるため新 ADR を起票する
- `category_source` の更新等、ハッシュ対象外の列は冪等性に影響しない設計とする
