# ADR-008: カテゴリ分類は3層戦略（ルール→LLM→手動）

## ステータス
採用済み

## 背景

設計書 §6.1 のとおり、支出分析を実用にするには 80% 以上の自動分類精度が必要である。家計の取引には以下の傾向がある。

- 食費・交通費・固定費は反復性が極めて高い（同じ店、同じ事業者、同じ金額帯）
- 一方で旅行先の店舗・新しいサブスク・初めての EC モール購入など、未知パターンも継続的に発生する
- 全件を手動分類すると週次運用 30 分の制約（設計書 §9.1）を超過する

単一手段では網羅性と精度の両立が難しい。

## 検討した選択肢

### 選択肢A. ルールエンジンのみ
- メリット: 高速、安定、決定的、コストゼロ
- デメリット: 未知パターンに弱い。新店舗・新サブスク追加のたびにルール手書きが必要

### 選択肢B. LLM のみ
- メリット: 未知パターンに対応可能、ルール保守不要
- デメリット: 推論コスト・レイテンシ、確信度の低い分類が混入、決定性がない（同一入力で結果が揺れる可能性）、API 障害時に全体停止

### 選択肢C. 3 層戦略（ルール → LLM → 手動）
- メリット: 反復系はルールで決定的に、未知系は LLM で推定、最終補正は人間が行いつつルール化提案で学習。3 段階の信頼度を区別可能
- デメリット: 実装層が増える。`category_source` の管理が必要

## 決定

選択肢 C を採用する。設計書 §6.1 のフローに従い、以下の順序で分類する。

1. 新規取引が到着したら、`categorization_rules` を優先度順に評価
2. マッチすれば `category_source = 'rule'` で確定
3. マッチしなければ Anthropic API（LLM）に送信し、`category_source = 'llm'` で記録
4. 確信度が低い・LLM が無効な場合は未分類のまま保存
5. ユーザが UI で修正したら `category_source = 'manual'` を記録し、「このパターンを今後もこのカテゴリにしますか？」とルール化提案

## 理由

- ルール層は反復取引（食費・交通費・固定費）を低コスト・高速・決定的にカバーする。最初に手動で 100 件程度書けば 9 割をカバーできる見込み（設計書 §6.2）
- LLM 層は未知パターンに強く、ルール未マッチのみへの呼び出しなのでコスト・レイテンシが無視できる範囲（月数百件）
- 手動修正からのルール化提案は MoneyForward の挙動（設計書 §6.4）と同等で、運用を続けるほどルール網羅率が上がり LLM 依存度が下がる自己学習構造になる
- `category_source` を保持することで、信頼度の異なる分類を区別でき、将来的な再学習・精度監査の対象を機械的に特定できる

## 結果

- `transactions.category_source` 列が必須となる（`CHECK IN ('rule','llm','manual')`、設計書 §4.2）
- ルールエンジンは regex / contains / exact の 3 マッチタイプを優先度順に評価する単純設計（設計書 §6.2）
- LLM プロンプトは「日本の家計簿カテゴリ」を明示し、確信度しきい値を持たせる
- カテゴリ修正 UI は単なる編集に留まらず、ルール化提案 UX を必須要件とする（設計書 §6.4）
- LLM コスト監視のため、月次の API 利用量レポートを運用に組み込む（設計書 §9 の拡張余地）

## 関連

- ADR-004（PostgreSQL 16 + JSONB）: `transactions` に `category_source` 列を保持する前提
- ADR-006（hash UNIQUE による冪等性）: `category_source` はハッシュ対象外であり、再分類しても冪等性を壊さない
