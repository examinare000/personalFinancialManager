# ADR-010: UIアクセスをTailscale経由のみに限定

## ステータス
採用済み

## 背景

本アプリケーションは家計データという極めて機密性の高い情報を扱う。設計書 §2.3 / §10.1 で示されるとおり、Web UI を外部ネットワークに直接公開することは攻撃面を著しく拡大する。

一方で、ユーザ自身は外出先からダッシュボードにアクセスしたいケースがある。このため「外部公開しない、しかし本人はどこからでも到達可能」という両立が必要。

## 検討した選択肢

### 選択肢A. パブリック公開 + アプリ層認証
- メリット: 設定が単純、どこからでもアクセス可
- デメリット: NAS の IP / ドメインが世界中に晒される。アプリ層脆弱性・依存パッケージ脆弱性が即座に攻撃面になる。家計データの機密性に対して攻撃面が広すぎる

### 選択肢B. 従来型 VPN（OpenVPN / WireGuard 等を自前運用）
- メリット: 標準的、自分で完全制御
- デメリット: NAT 越え・キー配布・モバイル端末でのプロファイル管理など、単独ユーザでも運用負荷が高い

### 選択肢C. Tailscale 等のオーバーレイネットワーク（または Cloudflare Tunnel）
- メリット: NAT 越え自動、デバイス認証は IdP（Google/Microsoft 等）に委譲、Funnel/Serve でユーザ自身のみアクセス可、運用負荷が極小
- デメリット: 第三者サービス（コーディネーション層）への依存

## 決定

選択肢 C を採用する。設計書 §7.2 / §10.1 のとおり、Web UI への外部公開は Tailscale 経由のみとする。Cloudflare Tunnel も代替候補として並行運用可能とする。

## 理由

- 設計書 §10.3 の脅威モデルにある「ネットワーク経由の侵入」の攻撃面を最小化できる
- Tailscale はコーディネーション層の関与のみで、トラフィックは原則 P2P 暗号化されるため、第三者サービスへの依存を持ちつつもデータ機密性は保たれる
- IdP に MFA を設定すれば、デバイス追加に MFA を強制できる
- WireGuard ベースで性能も十分、単独ユーザならコストもゼロ

## 結果

- `caddy` コンテナはパブリック IP / ドメイン公開を行わず、Tailscale ネットワーク内からの 443 のみ受ける
- NAS のルータ側で UI 用の外部ポート開放を行わない（設計書 §10.1 のチェックリスト）
- Tailscale 認証情報（マシン認証鍵）は Docker secret で管理する（→ ADR-011）
- Tailscale サービス断時は外部からアクセス不能になるが、単独ユーザ運用なら許容できる
- 将来、共有機能（設計書 §11）を追加する場合は閲覧者用のサブセット UI を別経路で公開する設計を新 ADR で検討する
- **範囲**: 本決定は inbound（UI へのアクセス）に限定する。コンテナの outbound 通信（メール取得・外部API呼出）は本決定の対象外
