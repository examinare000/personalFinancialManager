# ADR-011: 金融機関ログイン認証情報を一切保持しない

## ステータス
採用済み

## 背景

家計集約アプリの最大の事故シナリオは、各金融機関のログイン認証情報（ID / パスワード）が漏洩することである。一度漏洩すれば資産の不正出金・不正取引に直結する。

設計書 §2.3 / §10.2 では「金融機関のログイン認証情報を一切保持しない」ことが本設計の最重要事項として明記されている。本 ADR はこの方針を独立した決定として固定し、後続の実装で例外が混入することを防ぐ。

## 検討した選択肢

### 選択肢A. 認証情報を暗号化して保管（KMS / age / Vault 等）
- メリット: 一定の自動化が可能（自動ログイン → CSV DL 等のバックグラウンド実行）
- デメリット:
  - 暗号鍵自体が新たな保護対象になり、保護対象が再帰的に増える
  - 鍵漏洩時の被害が金融機関ログインそのもの = 最悪シナリオ
  - そもそも自動ログインは ToS 違反（→ ADR-003）であり、保管する意味がない

### 選択肢B. 認証情報を一切保持しない
- メリット:
  - 漏洩しうる対象がそもそも存在しないため、最大事故シナリオを構造的に排除
  - Docker secret / 環境変数の保護対象が API キーのみに絞られる
  - ToS 違反となる自動ログイン経路を実装上不可能にできる
- デメリット: CSV を週次で手動 DL する運用負荷（土曜朝 30 分、設計書 §9.1）

## 決定

選択肢 B を採用する。本プロジェクトは金融機関のログイン ID / パスワードを一切コード・DB・secret に保持しない。

保持する secret は以下に限定する（設計書 §10.2）。

| 認証情報 | 保管場所 | 用途 |
|---|---|---|
| 銀行・証券のログイン ID/PW | **保持しない** | 手動 DL 方式のため不要 |
| Gmail OAuth トークン | Docker secret | 読み取り専用スコープに限定（設計書 §10.2） |
| PayPal API Secret | Docker secret | 公式 API 接続用 |
| Anthropic API Key | Docker secret | LLM 分類用 |

## 理由

- 認証情報を持たなければ漏洩しえない、という構造的安全性が最強
- ハイブリッド取得方式（→ ADR-001）と整合し、自動ログインを不要にしている
- 自動ログインは ToS 違反（→ ADR-003）でもあり、保管する正当性自体がない
- Docker secret 管理対象が最小化されることで、運用ミスのリスクも下がる

## 結果

- 銀行・証券認証情報を扱うコードパス・DB 列・secret ファイルを実装に一切持ち込まない
- セキュリティチェックリスト（設計書 §10.1）に「ログイン ID/PW を保持していないこと」を含める
- Gmail OAuth は読み取り専用スコープ（`gmail.readonly`）に限定する
- PayPal API は Transactions 取得スコープのみ。Payments 系スコープは付与しない
- 将来、銀行が個人 OAuth 読み取り API を提供した場合は、リフレッシュトークンの保管方針を新 ADR で検討する（暗号化前提でも本 ADR を上書きする）
