# ADR-005: 金額・数量はNUMERICで保持しfloatを禁止

## ステータス
採用済み

## 背景

本アプリケーションは銀行残高・取引金額に加え、投資信託の口数（小数 6 桁以上の精度を要するケースが多い）も扱う（設計書 §4.2 の `holdings.quantity NUMERIC(18,6)`）。

浮動小数点（`float` / `double`）で金額・口数を保持すると以下が発生する。

- 二進浮動小数で表現できない 10 進小数（例: 0.1）の丸め誤差
- 集計時の誤差累積
- 残高整合性チェック（前日残高 + 当日取引合計 = 当日残高、設計書 §9.3）の不一致を誘発

設計書 §4.3 でも「`amount` NUMERIC、float 禁止」と明記されており、これを ADR として固定する。

## 検討した選択肢

### 選択肢A. DECIMAL / NUMERIC（任意精度小数）
- メリット: 厳密な 10 進演算、丸め誤差なし、PostgreSQL の `NUMERIC(p,s)` でスケール固定
- デメリット: float に比べ演算コストが高い（家計簿規模では無視できる）

### 選択肢B. double precision（IEEE 754 倍精度浮動小数）
- メリット: 演算が高速
- デメリット: 丸め誤差。金額・口数では絶対に許容できない

### 選択肢C. 整数（最小単位、円なら 1 円、口数なら 1/1,000,000 口など）
- メリット: 演算が高速、誤差なし
- デメリット: スケールがアプリ層の暗黙合意になり、SQL から直接見たときに値の意味が掴みにくい。通貨が増えた場合（USD はセント、JPY は円）にスケール統一の合意が困難

## 決定

選択肢 A を採用する。具体的には設計書 §4.2 のとおり以下のスケールで固定する。

| 列 | 型 | スケール |
|---|---|---|
| `transactions.amount` | NUMERIC(18,4) | 金額（4 桁小数までの通貨に対応） |
| `holdings.quantity` | NUMERIC(18,6) | 口数（投資信託の最小単位） |
| `holdings.market_value` | NUMERIC(18,4) | 評価額 |
| `holdings.unit_cost` | NUMERIC(18,6) | 取得単価 |
| `balance_snapshots.balance` | NUMERIC(18,4) | 残高 |

アプリ層（Python）では `decimal.Decimal` を使用し、`float` への暗黙変換を禁止する。

## 理由

- 投資信託の口数は 6 桁小数の精度が普通であり、`float` で扱うと買付・解約の累積で誤差が発生する
- 残高整合性アサーション（設計書 §9.3）が成立しなくなると、本アプリの信頼性そのものが崩れる
- 整数最小単位方式（選択肢 C）は将来の多通貨対応（設計書 §11）を見据えると合意コストが高く、NUMERIC のほうが拡張性が高い

## 結果

- DB 層は `NUMERIC` で型保証される
- Python 層では SQLAlchemy の Numeric 型 + `decimal.Decimal` を使用するコーディング規約を設ける
- パーサ実装時、CSV から `float()` でパースしてはならず、`Decimal()` を文字列経由で生成する
- テストでは丸め誤差検出の単体テストをアダプタごとに用意する（TDD 方針、agent-rules/11-testing-strategy.md）
