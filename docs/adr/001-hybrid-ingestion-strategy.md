# ADR-001: ハイブリッド取得方式の採用

## ステータス
採用済み

## 背景

本プロジェクトは MoneyForward 等の商用アグリゲーションサービスへの依存を断ち、自分自身でデータ主権を持つことを目的とする（設計書 §1.1）。一方で、対象 11 機関（銀行 3、証券・投信 3、EC 3、決済 2）からのデータ取得には以下の現実制約がある（設計書 §2.1, §2.2）。

- 日本の銀行オープン API は「電子決済等代行業者」契約が必須で、個人開発者は接続できない
- EC・銀行サイトの自動スクレイピングは ToS 違反であり、MFA・CAPTCHA・ロックアウトリスクで現実解にならない
- 完全自動化は不可能だが、毎日全件を手入力するのも非現実的

「完全自動化」と「現実的に運用可能」の間でバランスを取る方式が必要だった。

## 検討した選択肢

### 選択肢A. 銀行オープンAPI直結による全自動化
- メリット: 完全自動化、リアルタイム残高
- デメリット: 個人開発者は契約不可。ADR-002 で詳述

### 選択肢B. EC・銀行サイトのスクレイピングによる全自動化
- メリット: 既存サイトに対応すれば理屈上は全自動化できる
- デメリット: ToS 違反、MFA・CAPTCHA・サイト構造変化・ロックアウトの全リスクを抱える。ADR-003 で詳述

### 選択肢C. ハイブリッド（公式CSV手動DL + メールパース + 公式API + 手動入力）
- メリット: 法務・規制・ToS をすべてクリア。各機関の最も摩擦の少ない経路を選択できる
- デメリット: 週次の手動 DL 作業が残る（土曜朝 30 分想定）

## 決定

選択肢 C を採用する。具体的には設計書 §2.4 の方針に従い、以下を取得方式の組み合わせとする。

| 取得方式 | 適用対象 | 自動化レベル |
|---|---|---|
| 公式 CSV/PDF の週次手動 DL | 銀行・証券各社 | 半自動（DL は手動、パースは自動） |
| メール通知パース（Gmail MCP 経由） | EC 各社、銀行の入出金通知 | 自動（日次バッチ） |
| 公式 API | PayPal | 自動 |
| 手動入力 UI | 現金、その他補完 | 手動 |

## 理由

法務・規制・ToS・MFA の現実制約をすべて満たせるのは、複数手段を組み合わせる方式しか存在しない。

- 銀行・証券: 公式 CSV エクスポートはユーザ自身による正規アクセスであり、ToS と整合する（パースは取得後の自処理）
- EC: 公式の注文確認メールを Gmail OAuth 読取で受信することは Gmail 規約・各 EC 規約のいずれにも違反しない
- 決済: PayPal は公式 API（Transactions API）を提供しており規約上問題ない
- 補完: 現金等はそもそも自動化対象にならない

「単独ユーザの週次運用」というユースケース（設計書 §1.2, §1.4）であれば、土曜朝の 30 分の手動 DL は許容コストである。

## 結果

- 取込層は機関別アダプタを必要とする（→ ADR-007）
- 認証情報を保持する経路を持たないため、最大の事故シナリオである「認証情報漏洩」を構造的に排除できる（→ ADR-011）
- DL 忘れによる残高欠損が発生しうるため、月次オペレーションでチェック手順（設計書 §9.2）を組み込む
- 将来、銀行 API 直結が個人にも開放された場合は本 ADR を上書きする新 ADR を起票する
