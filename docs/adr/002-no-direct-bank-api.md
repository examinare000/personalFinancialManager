# ADR-002: 銀行オープンAPI直接接続を採用しない

## ステータス
採用済み

## 背景

設計書 §2.1 のとおり、日本の銀行が提供するオープン API は「電子決済等代行業者（金融庁登録事業者）」との契約に基づいて利用される枠組みである。MoneyForward / Zaim 等の家計簿サービスは、このスキームの登録業者として接続している。

本プロジェクトは個人利用を前提とした自宅運用アプリケーション（設計書 §1.2）であり、開発者本人が登録業者になるという選択肢は実務上存在しない。にもかかわらず「銀行 API 直結」を選択肢として残しておくと、後続の設計（認証情報保管・監査要件等）が肥大化するため、早期に却下決定を残す必要があった。

参考: 設計書 §付録B
- 全国銀行協会「オープン API って何？」: https://www.zenginkyo.or.jp/article/tag-g/9797/
- 三菱UFJ銀行「電子決済等代行業者との契約内容」: https://www.bk.mufg.jp/ippan/law/dendaigyousha/keiyaku.html

## 検討した選択肢

### 選択肢A. 銀行オープンAPIへの直接接続を試みる
- メリット: 残高鮮度がリアルタイム、運用負荷ゼロ
- デメリット:
  - 電子決済等代行業者として金融庁登録が必要（個人不可）
  - 各銀行との個別契約が必要（個人と契約してくれる銀行は存在しない）
  - 接続維持コスト・監査対応・障害時の対外通報義務など、個人運用の規模に見合わない

### 選択肢B. 銀行オープンAPI直結を採用しない
- メリット: 法務・契約・監査要件から解放される。設計が簡潔になる
- デメリット: 残高取得が手動 DL に依存（週次バッチが許容できる前提なら問題なし）

## 決定

選択肢 B を採用する。本プロジェクトは銀行オープン API への直接接続を行わない。

## 理由

- 個人開発者は電子決済等代行業者として登録できず、銀行と直接契約も結べない
- 仮に技術的に何らかの抜け道が存在したとしても、それは ToS / 業法上のグレーであり本プロジェクトの「ToS に抵触しない方式のみ採用」（設計書 §2.1）方針に反する
- ユースケースが「週次の残高鮮度で十分」（設計書 §1.4）であるため、API 直結の必要性自体が薄い

## 結果

- 銀行データの取得は公式 CSV 手動 DL に一本化される（→ ADR-001、設計書 §5.1）
- 銀行ログイン認証情報を保持する必然性が消え、ADR-011（認証情報を保持しない）の前提となる
- 将来、個人が利用できるオープン API スキーム（例: ユーザ自身による OAuth 同意ベースの読み取り API）が一般提供された場合は、本 ADR を上書きする新 ADR を起票する
