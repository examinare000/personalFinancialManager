# ADR-017: 取引ハッシュ生成規則への生ペイロードの追加

## ステータス
採用済み

## 背景

ADR-006 において、取引の冪等性（二重取込防止）を確保するために `SHA-256(account_id || occurred_on || amount || description)` をハッシュ UNIQUE 制約として採用した。しかし、Phase 1 の詳細設計（`postgres/docs/design/01-data-model.md`）の過程で、以下の課題が浮上した。

- **正当な重複取引の拒絶**: 同一日に、同一店舗で、同一金額の買い物を複数回行った場合（例：コンビニでの数回購入）、ハッシュ値が衝突し、2 件目以降が DB 側で重複として拒絶されてしまう。
- **情報の欠落**: 摘要（description）に時刻が含まれない CSV フォーマットの場合、上記の問題が顕著になる。

一方で、原本データ（`raw_payload`）には、機関側が保持する一意な情報（行番号、処理時刻、内部シリアル番号等）が含まれていることが多く、これを利用することで実質的な一意性を担保できる。

## 検討した選択肢

### 選択肢A. 現状維持（ADR-006 のまま）
- メリット: 実装が単純。
- デメリット: 正当な重複取引が取り込めない運用制限が発生する。

### 選択肢B. ハッシュキーに `raw_payload` を追加（採用）
- メリット: 同一 CSV 行であれば必ず一意になり、かつ同一 CSV の再投入は確実に防げる。
- デメリット: `raw_payload` の微細な差分（パース時の浮動小数点誤差等）でハッシュが変わるリスクがあるため、カノニカル（正規化）な JSON 文字列化が必要。

## 決定

選択肢 B を採用する。取引ハッシュの生成規則を以下に更新する。

```
hash = SHA256(
  account_id || '|' ||
  occurred_on || '|' ||
  amount || '|' ||
  description || '|' ||
  raw_payload_canonical_json
)
```

`raw_payload_canonical_json` は、原本の JSON データを再帰的にキーソートして文字列化したものとする。

## 理由

- 正当な重複取引（同日・同店・同額）を安全に許可しつつ、同一 CSV / 同一メールの再取込を 100% 防止できるため。
- ADR-004 で `raw_payload` を JSONB で保持することを決定しており、そのデータレイク的な価値を冪等性担保にも活用するため。

## 結果

- アダプタ層で `raw_payload` を構築する際、パース対象の行全体を確実に含める必要がある。
- `Transaction` 共通型（ADR-018）において、ハッシュ計算ロジックに `raw_payload` を組み込む。
- 既存の ADR-006 を本 ADR で上書き（Supersede）する。
