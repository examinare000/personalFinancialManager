# ADR-003: EC・銀行サイトスクレイピングを採用しない

## ステータス
採用済み

## 背景

設計書 §2.1 のとおり、Amazon / 楽天 / Yahoo!ショッピング / PayPay 等は利用規約でスクレイピング・自動アクセスを明示的に禁止している。銀行サイトについても同様で、自動ログインは ToS 違反となる。

技術的にも、設計書 §2.2 で整理された以下の障壁により、スクレイピングは現実解にならない。

| 障壁 | 影響度 |
|---|---|
| 多要素認証（SMS OTP / トークン / 生体）の必須化 | 完全自動化が極めて困難 |
| デバイスフィンガープリンティング | 新環境からのログインで追加認証 |
| CAPTCHA / 行動分析 | 特に大手 EC で厳格 |
| サイト構造の頻繁な変更 | 継続的な保守工数 |
| ログイン試行のロックアウト | 解除が電話手続きとなる事故リスク |

このリスクを抱えるか否かは ADR-001 の前提となるため、独立した決定として明文化する。

## 検討した選択肢

### 選択肢A. ヘッドレスブラウザ等によるスクレイピングを採用する
- メリット: 公式 API のない機関でも自動化できる可能性がある
- デメリット: ToS 違反、MFA 突破不能、CAPTCHA、ロックアウト、サイト改修への追従コスト。事故時にアカウント凍結のリスクが高い

### 選択肢B. スクレイピングを採用しない
- メリット: ToS 遵守、ロックアウト事故ゼロ、保守工数ゼロ
- デメリット: 公式エクスポートを持たない機関は手動入力に頼る必要

## 決定

選択肢 B を採用する。本プロジェクトは EC・銀行・証券サイトに対するスクレイピングを一切行わない。

## 理由

- 設計書 §2.2 の障壁表が示すとおり、技術障壁の組み合わせ（MFA + フィンガープリンティング + CAPTCHA）に対して継続的に勝ち続ける現実解は存在しない
- 仮に技術的に成立しても ToS 違反である以上、ロックアウトや法的リスクを内包する
- 単独ユーザのアカウントでロックアウトが起きると、家計データそのものへのアクセスを失う最悪のシナリオに直結する

## 結果

- 取得方式は公式 CSV / 公式 API / 公式メール通知のみに限定される（→ ADR-001）
- 公式手段を持たない機関が将来追加された場合、手動入力 UI で補完する（設計書 §2.4）
- スクレイピング系のライブラリ（Selenium / Playwright 等）はプロダクション依存に含めない方針が確定する
