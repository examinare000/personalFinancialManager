# ADR-019: Alembic マイグレーションの分割管理方針

## ステータス
採用済み

## 背景

Phase 1.1 において、プロジェクトの初期スキーマ（7 テーブル）を Alembic で実装する。通常、初期スキーマは 1 つの `0001_initial.py` にまとめられることが多いが、本プロジェクトでは ADR-014 に基づくサービス境界の明確化と、アトミックな変更履歴の管理を重視している。

## 検討した選択肢

### 選択肢A. 単一の巨大なマイグレーションファイル
- メリット: 管理が単純。
- デメリット: テーブル間の依存関係がコード上で埋没し、レビューや将来の部分的な改修・ロールバックが困難。

### 選択肢B. テーブル/機能単位での分割（採用）
- メリット: 変更の論理単位が明確。マイグレーションファイル自体が設計の意図を示すドキュメントとして機能する。
- デメリット: ファイル数が増える。

## 決定

選択肢 B を採用し、Phase 1.1 の初期スキーマを以下の 5 つのマイグレーションファイルに分割して管理する。

1. `institutions` / `accounts`（基盤マスタ）
2. `categories`（分類マスタ）
3. `transactions`（フローデータ）
4. `holdings` / `balance_snapshots`（ストックデータ）
5. `categorization_rules`（分類ルール）

各ファイルは Alembic の `down_revision` によって線形に連結される。

## 理由

- 各テーブルの責務（マスタ、フロー、ストック、ルール）が明確に分かれており、それらを個別の変更単位として扱うことが ADR-014 の思想（サービス境界・関心の分離）と整合するため。
- 1 つの PR 内で 5 つのコミットに分けることで、設計レビューの精度を向上させ、履歴の追跡を容易にするため。

## 結果

- `postgres/src/alembic/versions/` 配下に 5 つのリビジョンファイルが生成される。
- 以降のスキーマ変更も、論理的な変更単位ごとに新規リビジョンを作成する運用を徹底する。
