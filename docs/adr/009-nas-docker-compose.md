# ADR-009: 自宅NAS + Docker Compose を運用基盤に採用

## ステータス
採用済み

## 背景

本プロジェクトは設計書 §1.1 にあるとおり「データ主権を自分で持つ」ことを目的とし、家計データという機密性の高い情報を扱う。一方で運用はコスト・学習機会・運用負荷のバランスを考慮する必要がある。

- 単独ユーザのスケール感（設計書 §1.2）
- 取込ワーカ・DB・API・UI・バックアップなど複数コンポーネントが必要（設計書 §3.1, §7.1）
- コストはランニングを最小化したい（家計簿アプリ自身が固定費を生むのは本末転倒）

## 検討した選択肢

### 選択肢A. クラウドマネージドサービス（RDS + ECS / Cloud Run + Cloud SQL 等）
- メリット: スケーラビリティ、マネージドバックアップ
- デメリット: ランニングコスト（DB だけで月数千円〜）、家計データを第三者クラウドに置くこと自体がデータ主権の方針に反する、単独ユーザには過剰

### 選択肢B. VPS（Linode / さくら VPS 等）
- メリット: ランニングコストはクラウドより安い
- デメリット: データが物理的に手元になく、データ主権という設計目的とずれる。NAS と二重管理になる

### 選択肢C. 自宅 NAS + Docker Compose
- メリット: データが物理的に手元、ランニングコスト最小、家庭内 LAN 内で完結、Docker Compose は学習しやすく Compose ファイル一枚で構成が再現可能
- デメリット: 自宅停電・回線断で停止する。単独ユーザ運用なら許容範囲

### 選択肢D. Kubernetes（k3s 等）
- メリット: 宣言的、スケール余地
- デメリット: 単独ユーザ・5〜6 サービス規模に対して圧倒的に過剰、運用負荷が大きい

## 決定

選択肢 C を採用する。設計書 §7.1 のとおり Synology / QNAP 等の家庭用 NAS 上に Docker Compose スタックを配置する。

サービス構成（設計書 §7.1）:
- `postgres`（PostgreSQL 16-alpine）
- `worker`（取込ワーカ）
- `api`（Flask）
- `ui`（React）
- `caddy`（リバースプロキシ）
- `backup`（pg_dump 日次バッチ）

## 理由

- 家計データの物理的所在を自宅内に閉じることで、データ主権という設計目的（設計書 §1.1）と整合する
- 単独ユーザ規模では Kubernetes / クラウドマネージドは明確に過剰
- Docker Compose ファイル 1 枚で構成全体が宣言的に表現でき、移設・バックアップが容易（→ ADR-012）
- NAS の RAID / スナップショット機能と Docker Compose のボリューム永続化が相性良い
- 学習機会としても、Compose は Kubernetes へのステップアップに繋がる

## 結果

- 物理障害時の単一障害点になるため、3 階層バックアップ（→ ADR-012）が前提となる
- 外部からのアクセスは Tailscale 経由のみ（→ ADR-010）。NAS の Web UI を直接公開しない
- `internal` / `external` の Docker ネットワーク分離（設計書 §7.2）を設計に組み込む
- 将来、複数ユーザに広げる場合は VPS / クラウドへの移行を検討する余地を残す（本 ADR は「単独ユーザ」前提）
