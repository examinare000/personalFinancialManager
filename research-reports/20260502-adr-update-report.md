# 調査報告書：Phase 1 着手に伴う ADR の更新と新規作成

## 調査概要
- **テーマ**: Phase 1（データモデル・共通型実装）の開始に伴うアーキテクチャ決定の再整備
- **期間**: 2026年5月2日
- **調査者**: Gemini-cli
- **対象ブランチ**: `development/research/adr-update-ph1`

## 主要発見事項
- **ADR-006 の限界**: 既存のハッシュ生成規則（account_id + date + amount + description）では、同一日に同一店舗で同一金額の買い物をした場合に衝突が発生し、正当な取引が取り込めないリスクがあることが詳細設計（`postgres/docs/design/01-data-model.md`）の過程で判明した。
- **実装方針の具体化**: Phase 1.1 のマイグレーション分割や、Phase 1.2 のドメインオブジェクト実装方針（dataclass 採用）など、実装に直結する重要なアーキテクチャ決定が設計ドキュメント内には存在するが、ADR として独立していなかった。
- **整合性の確保**: 最新の設計ドキュメント（2026-05-01 更新分）と既存の ADR との間に一部乖離（ハッシュ規則等）が生じていた。

## 推奨事項（実施済み内容）
1. **ADR-017 の作成**: ADR-006 を上書きし、ハッシュ生成規則に `raw_payload_canonical_json` を追加。これにより、正当な重複取引を許容しつつ、同一データの再投入を確実に防ぐ。
2. **ADR-018 の作成**: ドメインオブジェクト（Transaction 等）の実装に `dataclass(frozen=True, slots=True)` を採用することを決定。Phase 1 では軽量さを優先し Pydantic の導入を保留。
3. **ADR-019 の作成**: 初期スキーマのマイグレーションを 5 つの論理単位に分割することを決定。変更履歴の追跡性とレビュー品質を向上。
4. **設計・計画ドキュメントの更新**: 上記 ADR の新設に合わせて、`01-data-model.md` や各タスクプラン（Ph1/02, 03）の参照先を更新。

## 技術的詳細
### 1. ハッシュ規則の変更
`raw_payload` を SHA-256 の入力に含めることで、原本データが 1 ビットでも異なれば別の取引として扱われる。これにより、銀行 CSV の行番号や時刻情報の差分がハッシュに反映され、重複判定の精度が劇的に向上する。

### 2. dataclass の採用
`frozen=True` による不変性は、TDD サイクルにおいて副作用を排除するために極めて有効である。また、`slots=True` は Python 3.10 以降で利用可能なメモリ最適化手法であり、大量の取引データを扱う Worker サービスに適している。
